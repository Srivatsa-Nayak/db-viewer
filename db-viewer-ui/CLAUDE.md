# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Commands

```bash
npm run dev      # start dev server (http://localhost:3000)
npm run build    # production build
npm run start    # run production build
npm run lint     # eslint (flat config in eslint.config.mjs)
```

There is no test suite in this repo. There is no single-file lint/typecheck shortcut beyond `npm run lint`; use `npx tsc --noEmit` for a type-only check.

The backend (sibling directory `../db-viewer-backend`, Spring Boot / Java 17) must be running on port 8080 for the UI to do anything useful: `./mvnw spring-boot:run` (or `mvnw.cmd spring-boot:run` on Windows) from that directory. Swagger UI is at `http://localhost:8080/swagger-ui.html`.

## Environment

The backend base URL comes from `NEXT_PUBLIC_API_URL`, falling back to `http://localhost:8080` (`services/api.ts`). Env files present: `.env.local`, `.env.production`.

## Architecture

This is a Next.js (App Router) single-page workspace app for importing CSV/SQL files, visualizing schema as a graph, editing table data, and exporting. There is no in-app SQL query runner — that panel (`SqlEditor`/`ResultsTable`/`useQuery`, plus `dbService.runQuery`/`POST /query`) was removed; if it needs to come back, it must be re-added as a sibling of the canvas, not nested inside `Visualizer.tsx`. Nearly all state lives in one place:

- **Routes:** `/` is the landing page (`app/page.tsx` — marketing only, no workspace state), `/app` is the editor (`app/app/page.tsx`), `/docs` is the manual, `/share/[token]` is the read-only shared view. Anything below describing "the page" means the **editor** at `app/app/page.tsx`.
- **The landing page and the docs run the real canvas, not pictures of it.** `components/landing/DemoCanvas.tsx` is a React Flow canvas with a compact read-only node and the editor's own `OrthogonalEdge`, taking its schema from a literal in the caller. It is `next/dynamic` + `ssr: false` everywhere it is used, because it is ~50KB those routes otherwise have no use for; the hero's loading fallback is the old CSS mock (`HeroDiagram`) at the same size, so nothing shifts. **It is controlled, so it must keep its `onNodesChange`, and that handler must be `applyNodeChanges`** — two separate traps, both of which were hit. Without any handler React Flow computes a drag and silently discards it, which looks exactly like a canvas that was never draggable. With a hand-rolled handler that rebuilds the node array from props each frame, it drags correctly and *strobes*: a fresh object per node makes React Flow rebuild all of its node internals, and on the frames before those are measured again an edge cannot resolve its handles, so **every relationship line disappears** — measured at a quarter of the frames of a drag. `applyNodeChanges` returns the same objects for untouched nodes, which is why the editor never had the problem. Consequences: `tables` is the **initial** layout (both callers remount with a `key` when the schema changes, which also resets the bloom), and anything presentational that varies per node — the refused-delete styling — goes on the node's `className`, never into `data`, so `data` identity survives a drag. `autoPanOnNodeDrag` is off: on a canvas this small React Flow starts panning almost immediately and slides the diagram out from under the cursor.
- **`components/landing/FeaturesSection.tsx` is a rail plus one sticky demo panel**, not a grid of cards: hovering or focusing a feature plays that action in the panel. The scenes live in `FeatureDemos.tsx` and are built from the app's own tokens rather than recorded as GIFs — they cost a few kilobytes for all ten, stay sharp, follow the theme and cannot show a build that no longer exists. They animate through one shared vocabulary (`.fx` + `.fx-in` / `.fx-fade` / `.fx-out` / `.fx-draw` / `.fx-press`… in `globals.css`), sequenced by a `--fx-delay` custom property, and every scene lays itself out in one 260x150 design space expressed as percentages — a scene positioned in pixels comes apart the moment the panel is a different size, which it is on a phone. **Do not put `overflow-hidden` on that section**: a clipped ancestor becomes the scroll container for `position: sticky`, and the panel stops sticking without any CSS appearing to be wrong.
- **`components/landing/DatabaseLogos.tsx`** holds the engine marks. The outlines come from Simple Icons (CC0); SQL Server is drawn by hand because Microsoft's marks are not in that set and their guidelines do not allow redrawing the official one. Each renders in `currentColor` so one tile can show it branded, muted or white.
- **Templates are backend-owned.** `GET /templates` returns the catalogue; `components/landing/TemplatesSection.tsx` only renders it. Adding a template is a backend-only change (a `.sql` file plus a `manifest.json` entry) — do not hardcode template metadata in the frontend. The landing page starts a template by creating a workspace, calling `POST /templates/{id}/apply`, appending to the stored session and pushing to `/app`; the editor's existing restore path does the rest.
- **`app/app/page.tsx`** is the owner of almost everything: `workspaces`, `activeWorkspaceId`, explorer open state, table-editing state, and upload/clear/notice/info modal state. `refreshActiveSchema` is intentionally `useCallback(..., [])` and reads `activeWorkspaceIdRef.current` — every node captures it in `data.onRefresh`, and a closure over the `activeWorkspaceId` *state* is stale for a freshly created file (it is still the previous id, `null` for the first file), which made the canvas silently not update after a column edit. Don't add dependencies to it. It also contains the schema→React-Flow transform (`transformSchemaToWorkspace`) and refresh logic. Start here for any workspace-level behavior change.
- **Workspaces are backend-isolated.** Each open file's `id` *is* a backend workspace id, sent on every request as the `X-Workspace-Id` header (see `services/api.ts`), and the backend keeps a separate database per id. Two files can define the same table names. `setActiveWorkspace()` is called both from a `useEffect` on `activeWorkspaceId` **and synchronously** in `handleFileUpload`/`handleCreateBlankFile` — the synchronous call is load-bearing, because those two generate an id and call the API in the same tick, before the effect runs. Workspace ids come from `services/workspaceId.ts` (`newWorkspaceId()`), never `Date.now()` — two files created in the same millisecond used to collide onto a single backend database.
- **`services/api.ts`** centralizes every backend call (`dbService`) **and normalizes the wire format**. The backend has shipped both `is_pk` and `isPk` (and `source_table`/`sourceTable`, `not_null`/`notNull`); `normaliseColumn` / `normaliseRelationships` / `normaliseSchema` fold both spellings into the camelCase shapes in `types/index.ts` at the boundary, so no component should ever write `c.is_pk ?? c.isPk` again. Normalize new response-reading endpoints here too. Endpoints: `POST /import/analyze`, `POST /upload`, `POST /alter-table`, `GET /db-info`, `GET /export/{tableName}`, `GET /table-data/{tableName}`, `POST /update-cell`, `POST /insert-row`, `POST /delete-row`, `DELETE /workspace`, `GET /export-sql`, `POST /create-table`, `POST /update-column`, `GET /version`, `GET /workspaces`, `POST /workspace/name`, `DELETE /table/{name}`, `POST /demo`, `/table-notes...`, `/auth/*`, `/share*`, `GET /templates`, `GET /templates/{id}`, `POST /templates/{id}/apply`, `GET /dialects`. Exports go through Axios as blobs, not `<a href>`, because a link cannot carry the `Authorization` header those endpoints now require. `uploadFile` returns an `UploadReport` (`statementsExecuted`/`statementsSkipped`/`warnings`/`dialect`) — surface it via `NoticeModal`, don't drop it. `uploadFile(file, columnTypes?)` and `downloadDatabaseSql(name, dialect)` both take an extra argument that changes what the backend does; neither is optional in the sense of "safe to forget" — see the import and export bullets below. Most cache-sensitive reads append a `_t`/`t` timestamp query param to bust caching.
- **`GET /workspaces` is the authority on which files exist; localStorage only remembers where the nodes were.** `services/sessionStorage.ts` (key `sql-visualizer.session`) stores ids, filenames and node positions — never the schema, which is always re-fetched so it cannot go stale. `restoreOpenFiles` in `page.tsx` builds the file list from the **backend** list and uses storage only for layout and as a name fallback; if the backend is unreachable it leaves the current list alone rather than emptying it. It was the other way round once — the stored session *was* the list — and that is a bug, not a preference: signing out clears localStorage, so it destroyed the only record of a signed-in user's files, and nothing re-listed them afterwards. **`restoreOpenFiles` re-runs whenever the identity changes** (`user?.email`), because signing in and out both change which files are yours and neither is a page load; the first run waits on `isAuthResolved` so it does not fire once as nobody and again as the user. Saving is debounced 300ms because node dragging fires `onNodesChange` continuously, and it is skipped while `isRestoring` so the first render cannot overwrite storage with an empty list.
- **Workspaces are owned, and the ownership is enforced by a filter.** Every workspace belongs to `user:<email>` (signed in) or `anon:<clientId>` (signed out), recorded in `workspace_owners` in the *default* database. `WorkspaceOwnershipFilter` claims a workspace for the first identified caller to touch it and answers 403 (`notYourWorkspace: true`) to anyone else, so a new endpoint is covered the moment it is written. `GET /workspaces` is scoped to the caller. The browser's identity comes from `X-Client-Id` (`services/clientId.ts`, localStorage), sent on every request beside `X-Workspace-Id`. On sign-in/sign-up the backend re-keys that browser's anonymous workspaces onto the account, so making an account does not strand the work that led to it — and it only ever moves workspaces that are *still* anonymous, so a second user on a shared browser cannot inherit the first one's files. **Signing out clears the open-files list** in the UI, because those workspaces would now 403 — and signing back in rebuilds it from `GET /workspaces`. The file **name** is stored server-side in `workspace_owners.file_name` (set via `POST /workspace/name` from every path that creates a file: upload, blank file, example, and the landing page's template launch). If you add a fifth way to create a file, name it too, or it comes back as "Untitled.sql". Handle 403 with `isForeignWorkspace(e)`, not `isAuthRequired(e)`: the caller is identified fine and signing in again would not help.
- **`CorsFilter` runs at `HIGHEST_PRECEDENCE`, ahead of every application filter.** Ordering is load-bearing, not tidiness: `WorkspaceOwnershipFilter` short-circuits with 403, and a response that never reaches the CORS filter carries no `Access-Control-Allow-Origin` — the browser then refuses to show the body, so the frontend sees an opaque network failure instead of a 403 it knows how to explain. Any new short-circuiting filter inherits this constraint.
- **Accounts are optional but enforced server-side.** Everything works signed out except exporting and creating a share link, which return 401. Gate in the UI *and* let the backend reject — `isAuthRequired(e)` turns a 401 into the sign-up prompt. Callbacks stored in node `data` (e.g. `handleDownloadCsv`) must read `userRef.current`, never the `user` state, or they pin to the first render's `null`.
- **A React Flow edge needs a `Handle` on both ends or it silently does not render.** The shared-file page (`app/share/[token]/page.tsx`) has its own read-only node, and originally drew no handles at all - so relationship lines never appeared even though the API returned them. It now derives the required `sourceColumns`/`targetColumns` per table from the relationships themselves (not from `*_id` naming like `TableNode` does) and sets `sourceHandle`/`targetHandle` on every edge. Any new custom node that edges attach to must do the same.
- **`services/exportImage.ts`** renders the canvas to PNG. It sizes the image from `getRectOfNodes` rather than the visible pane, so the export is not clipped to whatever is on screen.
- **`types/index.ts`** holds the shared types (`ColumnInfo`, `TableInfo`, `Relationship`, `SchemaResponse`, `TableDataResponse`) **plus the `Raw*` wire shapes**. The normalized types *are* ground truth now, because `services/api.ts` guarantees them; the `Raw*` types should be imported only by `services/api.ts`.
- **`components/canvas/Visualizer.tsx`** + **`components/tables/TableNode.tsx`**: the React Flow schema canvas. It owns the minimap, the search panel and the zoom control, and it is fully theme-aware — see the theming bullet. `TableNode` places its *handles* from the **relationship list** (`data.foreignKeyColumns` / `data.referencedColumns`, built by `keyColumnsByTable` in `page.tsx`), falling back to the `id` / `*_id` naming convention. The fallback is not decoration: a schema whose foreign key is called `customer` rather than `customer_id` used to get no handle and therefore no edge at all, silently, even though the backend had reported the relationship. Primary keys are gold (`text-key-pk`, a key icon) and foreign keys blue (`text-key-fk`, a link icon) — two hues *and* two shapes, because at the zoom where a hundred tables fit on screen the icons are four pixels wide. The canvas is deliberately **not** connectable (`nodesConnectable={false}`, and every `Handle` sets `isConnectable={false}`): the old no-op `onConnect`/`onEdgesChange` meant dragging a handle started a connection gesture the app could not honour. Relationships are created through `CreateTableModal`'s FK fields, which do persist. If drag-to-create is ever built, re-enable connectability *and* wire it to a backend call in the same change.
- **Theming is token-flipping, not a second stylesheet.** `app/globals.css` declares the light palette in `@theme`; `[data-theme="dark"]` redefines the *same* custom properties, and because Tailwind v4 emits every utility as a `var()` reference, the whole product flips without a single utility class changing. That is the difference from the dark mode that was removed before, which restyled the canvas by hand and left the rest of the chrome light. Consequences for new code: use `bg-surface`, not `bg-white`; use `bg-scrim/60` for an overlay, never `bg-ink-900/50` (the ink scale inverts, so an inverted scrim is a white flash); use the `tone-info` / `tone-warning` / `tone-error` / `tone-success` classes for tinted blocks rather than a `bg-red-50 border-red-200 text-red-700` triple. A `dark:` variant exists (`@custom-variant`, wired to the attribute rather than `prefers-color-scheme`) for the few colours a token cannot express — reach for it last. The preference lives in `services/theme.ts` (`light` / `dark` / `system`, localStorage) and is applied by a **blocking script in `app/layout.tsx`** before first paint; without it every load flashes white. **The default is `light`, not `system`** — the product should not look like two different things depending on whose machine opens a shared link — and the bootstrap script's fallback has to stay identical to `readPreference()`'s, or the first paint and the toggle disagree for a frame. `ThemeToggle` reads that preference through `useSyncExternalStore`, not `useState` + an effect, because the lint config rejects `set-state-in-effect` and because a second tab changing the theme should be picked up.
- **React Flow's own chrome is the one thing tokens cannot reach.** Its stylesheet is imported from a component, so it lands *after* `globals.css` in the bundle and wins any tie — every override of `.react-flow__*` is therefore prefixed with `.react-flow` purely for specificity. The background dot colour is the other exception: React Flow writes it to the pattern's `fill` **attribute**, where `var()` is not valid, so it is set from CSS instead and the `color` prop is only a fallback.
- **Navigation is built for a hundred tables, not six.** The minimap is a React Flow `MiniMap` sized through its `style` prop (a width utility lands on the panel and leaves the svg at its default 200x150) and hidden below `sm`. `components/canvas/CanvasSearch.tsx` is bound to **Ctrl+F**, which the canvas takes from the browser — defensible only because the browser's find bar genuinely cannot see table names inside a transformed viewport, and it stands down while a dialog is open (`document.body.dataset.dialogOpen`). Selecting a hit pans and zooms to the node and *dims everything else* (`.node-dim` / `.node-hit`); dimming rather than highlighting, because a highlighted node on a hundred-table canvas is still one of a hundred.
- **Edges are orthogonal and route around nodes.** `components/canvas/OrthogonalEdge.tsx` renders them, `edgeRouting.ts` decides the path. It is deliberately *not* a general pathfinder — a visibility graph or an A* over a grid is the textbook answer and far too slow to run on every frame of a node drag. It proposes a handful of candidate shapes (straight, one vertical channel, a lane above or below, a clear lane under everything), scores each on collisions, length and bend count, and takes the best. Obstacles come from React Flow's store rather than from props, because they must be the *current* positions, and they exclude the edge's own two nodes. If you add a node type, it becomes an obstacle automatically.
- **Importing is two steps, and the first one creates nothing.** `POST /import/analyze` returns an `ImportPlan` (tables, columns, inferred types with the *reason* for each, sample values, detected dialect, everything that will be skipped); `ImportPreviewModal` shows it; only on confirm does `POST /upload` run with the user's corrections as `columnTypes`. This is not a nicety. Type inference on a CSV is guesswork — every value in the file is a string — and the guess that matters is a postcode column of `01234`, which is all digits, becomes `INT`, and has lost its leading zeros before the canvas renders, unrecoverably. `handleFileChosen` is step one and `handleFileUpload(file, overrides)` is step two; the `File` itself is held in state between them so the confirm cannot import something different from what was previewed.
- **Exports go through one dialog, `ExportModal`, because the formats ask questions a menu line cannot.** SQL is generated **for a chosen engine** (`SQL_DIALECTS` in `services/api.ts`, sent as `?dialect=`): `AUTOINCREMENT`, `SERIAL`, `IDENTITY(1,1)` and `AUTO_INCREMENT` are four spellings of one idea and no engine accepts another's, so an untargeted script is only ever nearly runnable. Mermaid and DBML are generated **entirely in the browser** from the same `tables` + `relationships` the canvas draws (`services/exportDiagram.ts`), and PNG never leaves the DOM either — but all four formats still require an account. `ExportModal`'s `needsAccount` is `!hasAccount`, checked without regard to `format`, on purpose: it used to be `format === 'sql' && !hasAccount`, which let PNG, Mermaid and DBML download or copy while signed out, since nothing on the backend was there to answer 401 for formats that never call it. The UI check is the *only* enforcement those three have, so a new caller of `onExportImage`/`copyText` must not bypass `ExportModal`'s gate — `handleExportImage` in `page.tsx` re-checks `user` for the same reason `handleDownloadCsv` does. Mermaid drops a precision containing a comma (`DECIMAL(10,2)` → `DECIMAL`) because a comma inside parentheses fails Mermaid's parser and takes the whole diagram with it.
- **Dropdowns share `components/ui/useDismissable.ts`** — the editor's app bar and the landing nav both hang a menu off a button, and the hook owns outside-click and Escape for both. It listens for `mousedown` **in the capture phase**, and that is load-bearing: React Flow's pane calls `stopPropagation()` on its own pointer handlers, so a bubble-phase listener never hears a click that lands on a canvas, and both menus sit directly above one. A new dropdown uses this rather than a third copy.
- **The landing nav's three clusters all take part in the layout** (`components/landing/LandingNav.tsx`). The middle links were once `absolute left-1/2 -translate-x-1/2`, which centres them perfectly and lets the other two grow straight over them — signed in, the right-hand cluster was four controls wide and printed the theme toggle on top of "Docs". Equal `flex-1` gutters keep the links optically centred *and* reserve their space. The account control is one avatar menu, not a row of pills, for the same reason; the name is `lg:`-only so a long one cannot be what pushes the bar apart. Signed in, the bar carries the theme toggle and the account menu and nothing else: there is deliberately no "Open app" button, because the page's own calls to action already lead there and a nav button that appears only after signing in reads as an accident.
- **Every dialog goes through `components/ui/Modal.tsx`.** Do not hand-roll another overlay. The primitive owns the portal (always — a `position: fixed` descendant of React Flow's transformed viewport anchors to the canvas pane, not the window), Escape-closes only the top of the dialog stack, traps and restores focus, locks body scroll, sets `role="dialog"` / `aria-modal` / `aria-labelledby`, and derives its z-index from stack depth so nested dialogs never need a hand-picked `z-[130]`. It ships `ModalActions`, `PrimaryButton`, `DangerButton`, `GhostButton` and `Callout` for the furniture, and `components/ui/ConfirmDialog.tsx` for destructive confirmations. Below `sm` a dialog becomes a bottom sheet.
- **Dialogs are mounted only while open** (`{isOpen && <Foo isOpen ... />}`) and imported with `next/dynamic` + `ssr: false`. That is load-bearing twice: it keeps them out of the initial bundle, and it means *mounting is the reset* — which is why none of them re-seed form state from a `useEffect` any more, and why the old `key`-bumping remount trick is gone.
- **The docs page embeds live sandboxes rather than screenshots** (`components/docs/DocsSandbox.tsx`): the refused-delete demonstration runs the same rule the backend does, and the export panel calls the *production* exporter (`services/exportDiagram`), so it cannot print something the app would not. They are components, deliberately not an iframe of the editor — an embedded editor would need a real workspace, which means an upload, an owner and something to clean up, for a paragraph in a manual. `components/docs/DialectMatrix.tsx` is the support matrix; **every cell in it is a claim about `sql/SqlDialectTranslator`, `sql/SqlTypeMapper` or `sql/SqlExportWriter` on the backend** — change one of those and the matrix is wrong until it is changed too.
- **`components/modal/`**: `NewFileModal` (name a new file), `CreateTableModal` (full definition incl. FKs; one column per field below `lg`), `AddColumnModal` (single `ALTER TABLE`, opened from a table node's `+`), `EditColumnModal` (rename/retype, opened from the pencil on a column row — sends only the fields that changed, so a no-op save doesn't trigger a SQLite table rebuild), `ImportPreviewModal` (the pre-flight staging step — see above), `ExportModal` (every output format, one dialog), `NoticeModal` (error/warning with collapsible details, used for import reports), `InfoModal` (header help button: five-line app summary, version badge from `GET /version`, and developer credits — keep it to a glance, not a manual), `NewTableHelpModal` (canvas toolbar info button: what the New Table button does). The last two are intentionally *not* the same modal — help for a specific control belongs beside that control, the app summary belongs in the header.
- **`components/editor/DataEditor.tsx`**: row view/add/delete dialog with two editing modes — click a cell for a quick single-cell edit, or the row's pencil to edit every field at once with Save/Cancel (one `update-cell` per changed field; a partial failure names the fields that *were* written). A cell edit has exactly **one** commit path: `onBlur`. Enter and Escape both just call `blur()`, and Escape sets `abandonEditRef` so the blur skips the write — do not add a second commit to the key handler, which is what used to fire a duplicate `update-cell` on every Enter. Rows are keyed by their own `id`, never by array index. Update/delete paths assume every row has an `id` or `ID` field; a row without one has its buttons disabled rather than silently doing nothing.
- **Styling**: Tailwind v4, configured entirely from `app/globals.css` (there is no `tailwind.config.js`; the vestigial one pointing at `./src/**` was deleted). One palette for the whole product, declared in the `@theme` block: **`brand-*`** (blue 50-900 plus `brand-violet`) and **`ink-*`** (slate-valued neutrals 50-950), plus `surface`, `surface-tint`, `line`. Use those rather than raw `blue-*` / `zinc-*` / `slate-*` — the landing page and the editor used to run on two different systems, which is what made them read as two apps. Shared utilities: `brand-gradient(-hover)`, `brand-text-gradient`, `surface-card`, `section-wash(-tinted)`, `shadow-glow-sm/md/lg`, `scroll-slim`, and the `anim-*` animations. **There is no `tailwindcss-animate` plugin** — `animate-in` / `fade-in` / `slide-in-from-*` were inert at 17 call sites; use `anim-fade-in`, `anim-fade-up`, `anim-dialog-in`, `anim-menu-in`. An extra `xs` breakpoint (25rem) exists because Tailwind's smallest default is 640px. There is a dark theme, and it works by redefining the tokens rather than by adding classes — see the theming bullet above before adding any colour.
- **Responsive layout**: the editor shell is `h-[100dvh]`, not `h-screen` (mobile browser chrome). `FileExplorer` is a persistent column from `lg` up and an **overlay drawer** below it — absolutely positioned inside the `relative` content row, with a scrim rendered by `app/app/page.tsx`; selecting a file closes it on narrow screens. Its collapsed 48px rail is the only way back, so it renders at every width. The data table is the one element allowed to scroll sideways. Hover-only affordances (row actions, note delete) are `opacity-100` by default and only hover-gated from `sm` up, because touch has no hover.
- **Fonts**: two faces, both via `next/font/google` in `app/layout.tsx`. **Inter** drives `--font-sans` and the `body` rule — it is the UI face, and `globals.css` pairs it with the negative tracking and `cv02/cv03/cv04/cv11` features it is designed to be read with. **Geist Mono** drives `--font-mono`, so every `font-mono` utility (table/column names, filenames, zoom %, inline code in the docs) picks it up automatically. Keep monospace content on `font-mono` — column alignment depends on it — and don't hardcode a font-family per component.

## Suggested change workflow

1. Start from `app/app/page.tsx` for anything workspace-level; `app/page.tsx` is the landing page.
2. Check `services/api.ts` before adding/changing a backend call, and confirm the endpoint exists on the backend side (`../db-viewer-backend`, controllers under `src/main/java/com/dbviewer/app/controller/`).
3. Update `types/index.ts` when relying on new backend response fields.
4. New dialog? Use `components/ui/Modal.tsx`. New colour? Use a `brand-*` / `ink-*` / `tone-*` token and check it in **both** themes — `bg-white` and `bg-ink-900/50` are the two mistakes that look fine until someone switches. New password input? Use `components/ui/PasswordField.tsx` (it carries the reveal toggle).
5. Run `npx tsc --noEmit`, `npm run lint`, and `npm run build` after TypeScript/component edits. The lint config is strict about `react-hooks/set-state-in-effect` and `react-hooks/refs`; both usually mean the state should be derived, or the component should be mounted conditionally instead.
