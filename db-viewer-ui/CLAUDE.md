# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Commands

```bash
npm run dev      # start dev server (http://localhost:3000)
npm run build    # production build
npm run start    # run production build
npm run lint     # eslint (flat config in eslint.config.mjs)
```

There is no test suite in this repo. There is no single-file lint/typecheck shortcut beyond `npm run lint`; use `npx tsc --noEmit` for a type-only check.

The backend (sibling directory `../db-viewer-backend`, Spring Boot / Java 17) must be running on port 8080 for the UI to do anything useful: `./mvnw spring-boot:run` (or `mvnw.cmd spring-boot:run` on Windows) from that directory. Swagger UI is at `http://localhost:8080/swagger-ui.html`.

## Environment

The backend base URL comes from `NEXT_PUBLIC_API_URL`, falling back to `http://localhost:8080` (`services/api.ts`). Env files present: `.env.local`, `.env.production`.

## Architecture

This is a Next.js (App Router) single-page workspace app for importing CSV/SQL files, visualizing schema as a graph, editing table data, and exporting. There is no in-app SQL query runner — that panel (`SqlEditor`/`ResultsTable`/`useQuery`, plus `dbService.runQuery`/`POST /query`) was removed; if it needs to come back, it must be re-added as a sibling of the canvas, not nested inside `Visualizer.tsx` (see the fixed-positioning note below). Nearly all state lives in one place:

- **`app/page.tsx`** is the owner of almost everything: `workspaces`, `activeWorkspaceId`, explorer open state, table-editing state, and upload/clear/notice/info modal state. `refreshActiveSchema` is intentionally `useCallback(..., [])` and reads `activeWorkspaceIdRef.current` — every node captures it in `data.onRefresh`, and a closure over the `activeWorkspaceId` *state* is stale for a freshly created file (it is still the previous id, `null` for the first file), which made the canvas silently not update after a column edit. Don't add dependencies to it. It also contains the schema→React-Flow transform (`transformSchemaToWorkspace`) and refresh logic. Start here for any workspace-level behavior change.
- **Workspaces are backend-isolated.** Each open file's `id` *is* a backend workspace id, sent on every request as the `X-Workspace-Id` header (see `services/api.ts`), and the backend keeps a separate database per id. Two files can define the same table names. `setActiveWorkspace()` is called both from a `useEffect` on `activeWorkspaceId` **and synchronously** in `handleFileUpload`/`handleCreateBlankFile` — the synchronous call is load-bearing, because those two generate an id and call the API in the same tick, before the effect runs. Browser-initiated downloads can't set headers, so `getDownloadUrl`/`getDatabaseExportUrl` append `&workspaceId=` instead; any new download endpoint must do the same.
- **`services/api.ts`** centralizes every backend call (`dbService`). Check/extend this before adding new API calls anywhere else. Endpoints: `POST /upload`, `POST /alter-table`, `GET /db-info`, `GET /export/{tableName}`, `GET /table-data/{tableName}`, `POST /update-cell`, `POST /insert-row`, `POST /delete-row`, `DELETE /clear`, `DELETE /workspace`, `GET /export-sql`, `POST /create-table`, `POST /update-column`, `GET /version`, `GET /workspaces`, `DELETE /table/{name}`, `POST /demo`, `/table-notes...`, `/auth/*`, `/share*`. Exports go through Axios as blobs, not `<a href>`, because a link cannot carry the `Authorization` header those endpoints now require. `uploadFile` returns an `UploadReport` (`statementsExecuted`/`statementsSkipped`/`warnings`) — surface it via `NoticeModal`, don't drop it. Most cache-sensitive reads append a `_t`/`t` timestamp query param to bust caching.
- **Session persistence** lives in `services/sessionStorage.ts` (localStorage key `sql-visualizer.session`). It stores only ids, filenames and node positions — never the schema, which is always re-fetched from the backend on restore so it cannot go stale. `page.tsx` reconciles the stored list against `GET /workspaces` and drops entries whose database is gone; if the backend is unreachable it *keeps* the stored session rather than clearing it. Saving is debounced 300ms because node dragging fires `onNodesChange` continuously, and it is skipped while `isRestoring` so the first render cannot overwrite storage with an empty list.
- **Accounts are optional but enforced server-side.** Everything works signed out except exporting and creating a share link, which return 401. Gate in the UI *and* let the backend reject — `isAuthRequired(e)` turns a 401 into the sign-up prompt. Callbacks stored in node `data` (e.g. `handleDownloadCsv`) must read `userRef.current`, never the `user` state, or they pin to the first render's `null`.
- **A React Flow edge needs a `Handle` on both ends or it silently does not render.** The shared-file page (`app/share/[token]/page.tsx`) has its own read-only node, and originally drew no handles at all - so relationship lines never appeared even though the API returned them. It now derives the required `sourceColumns`/`targetColumns` per table from the relationships themselves (not from `*_id` naming like `TableNode` does) and sets `sourceHandle`/`targetHandle` on every edge. Any new custom node that edges attach to must do the same.
- **`services/exportImage.ts`** renders the canvas to PNG. It sizes the image from `getRectOfNodes` rather than the visible pane, so the export is not clipped to whatever is on screen.
- **`types/index.ts`** holds the shared types (`ColumnInfo`, `TableInfo`, `Relationship`, `SchemaResponse`, `TableDataResponse`). Some components already rely on fields not declared here (e.g. `is_pk`, `target_column`) — when you touch backend response shapes, update this file and the consuming components together rather than trusting the interface as ground truth.
- **`components/canvas/Visualizer.tsx`** + **`components/tables/TableNode.tsx`**: the React Flow schema canvas, light-theme only (the dark/system toggle was removed — it only ever restyled the canvas/table nodes, never the rest of the chrome, and looked inconsistent). `TableNode` infers PK/FK *handles* purely from column naming convention (`id` / `*_id`), not from real metadata — a column literally named `id` or ending in `_id` gets treated as a key. (`ColumnInfo` from the backend now does carry real `isPk`/`notNull`, which `EditColumnModal` uses to pre-fill; the handle heuristic was deliberately left alone.) React Flow's own edge-creation handlers in `app/page.tsx` are currently no-ops, so dragging a new relationship in the canvas does not persist anything to the backend.
- **Fixed-position modals must not be nested inside an animated/transformed ancestor.** `Visualizer.tsx`'s canvas wrapper has `animate-fade-up`, which sets a CSS `transform` — any `position: fixed` descendant then gets contained by that element's box instead of the viewport, silently shrinking to the canvas pane's width instead of centering on the full screen. `CreateTableModal` and `NewTableHelpModal` are rendered as siblings of that wrapper (via a `<>...</>` fragment) specifically to avoid this; `InfoModal` and `NoticeModal` live in `page.tsx`, outside the canvas. `AddColumnModal` opens from inside a `TableNode`, which is unavoidably deep inside React Flow's own transformed viewport, so it uses `createPortal(..., document.body)` with a `mounted` guard for SSR. Keep any new fixed-position modal either a sibling of `animate-fade-up`/transform-carrying elements, or portalled.
- **`components/modal/`**: `NewFileModal` (name a new file), `CreateTableModal` (full definition incl. FKs), `AddColumnModal` (single `ALTER TABLE`, opened from a table node's `+`), `EditColumnModal` (rename/retype, opened from the pencil on a column row — sends only the fields that changed, so a no-op save doesn't trigger a SQLite table rebuild), `NoticeModal` (error/warning with collapsible details, used for import reports), `InfoModal` (header help button: five-line app summary, version badge from `GET /version`, and developer credits — keep it to a glance, not a manual), `NewTableHelpModal` (canvas toolbar info button: what the New Table button does). The last two are intentionally *not* the same modal — help for a specific control belongs beside that control, the app summary belongs in the header.
- **`components/editor/DataEditor.tsx`**: row view/add/delete modal with two editing modes — click a cell for a quick single-cell edit (commits on blur/Enter, Escape cancels), or the row's pencil to edit every field at once with Save/Cancel (one `update-cell` per changed field). Update/delete paths assume every row has an `id` or `ID` field; a row without one has its edit button disabled rather than silently doing nothing.
- **`hooks/useSchema.ts`** is a legacy/alternate schema-state hook — the live app duplicates this logic directly in `app/page.tsx` instead of using it. Don't assume it's on the active code path.
- **Styling**: Tailwind v4 via CSS import (`app/globals.css`), not the JS config content-globbing convention — `tailwind.config.js` still lists `./src/**` paths that don't exist in this project (no `src/` dir) and appears to be vestigial from scaffolding. The UI is a fixed blue header / white body / blue-accent theme — there is no dark mode.
- **Font**: JetBrains Mono is loaded via `next/font/google` in `app/layout.tsx` and wired into Tailwind's `--font-mono` variable in `globals.css`, so every existing `font-mono` utility class (table/column names, filenames, zoom %, Monaco's `fontFamily`) picks it up automatically — don't hardcode a separate font-family per component.

## Suggested change workflow

1. Start from `app/page.tsx` for anything workspace-level.
2. Check `services/api.ts` before adding/changing a backend call, and confirm the endpoint exists on the backend side (`../db-viewer-backend`, controllers under `src/main/java/com/dbviewer/controller/`).
3. Update `types/index.ts` when relying on new backend response fields.
4. Run `npx tsc --noEmit`, `npm run lint`, and `npm run build` after TypeScript/component edits.
